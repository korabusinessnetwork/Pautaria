# ADR-007: Negar por omissão — privilégios padrão revertidos e pontes de serviço nominais

**Status:** Aceito
**Data:** 2026-08-17
**Decisores:** Matheus (dono)

## Contexto

O Postgres, e o Supabase por cima dele, são generosos por padrão:

- uma tabela nova em `public` já nasce com privilégio para `anon` e `authenticated`
  (`ALTER DEFAULT PRIVILEGES` do setup do Supabase);
- uma função nova já nasce com `EXECUTE` para `PUBLIC`;
- RLS vem **desligada** até alguém rodar `enable row level security`.

A combinação produz um modo de falha específico e conhecido: uma tabela criada às pressas
fica **legível pela internet** até alguém lembrar de ligar a RLS. E ninguém lembra — não
por descuido, mas porque nada avisa. O sistema falha aberto e em silêncio.

As migrations 0002–0007 protegeram as tabelas que existem. Faltava proteger as que **ainda
não existem**, que é onde brechas nascem.

Havia também uma tensão a resolver: as funções de defesa vivem no schema `app`, que fica
fora de `api.schemas` de propósito. Mas as Edge Functions falam com o banco pelo PostgREST,
que só enxerga `public`.

## Decisão

**Inverter o padrão: nada por omissão.**

1. **Privilégios padrão revertidos** para `postgres` e `supabase_admin` em `public` —
   tabelas, sequências e funções. Tabela nova nasce **inacessível**.
2. **`revoke create on schema public`** de `public`, `anon` e `authenticated`.
3. **Auditoria de cobertura como gate:** `app.tabelas_sem_rls()` lista tabelas sem RLS, ou
   com RLS ligada e nenhuma política mas com privilégio concedido. **Qualquer linha reprova
   o build** (Bloco 1 do teste de isolamento), e a reconciliação diária alerta em produção.
4. **Pontes de serviço nominais:** cada função de `app` que uma Edge Function precisa
   alcançar ganha uma ponte explícita em `public`, com `revoke all from public` +
   `grant execute to service_role`.

## Alternativas consideradas

### A — Manter os padrões do Supabase e confiar na disciplina
O que a maioria dos projetos faz. Descartada: disciplina não escala para o sábado às 23h.
O custo de errar aqui é vazamento de dado de todos os tenants.

### B — Expor o schema `app` inteiro na API e confiar nos grants
Resolveria a tensão em uma linha de `config.toml`. Descartada porque publicaria uma rota
HTTP para **cada** função interna — inclusive as que vierem depois, escritas por alguém que
não pensou em rota nenhuma. Superfície de ataque que cresce sozinha é a pior espécie.

Com pontes nominais, expor uma função nova exige escrever uma ponte nova, de propósito.

### C — Chamar as funções por SQL bruto via `service_role`
Evitaria as pontes. Descartada porque o supabase-js não expõe SQL arbitrário, e habilitar
isso seria abrir uma porta muito maior que a que se quer fechar.

### D — Linter de migration em vez de checagem em runtime
Analisaria o SQL procurando `create table` sem `enable row level security`. Descartada por
ser frágil (SQL tem muitas formas) e por não capturar tabela criada pelo painel do Supabase
— que é justamente o caminho mais provável do erro.

## Consequências

### Positivas
- **Esquecer passa a falhar fechado.** Uma tabela sem grants não funciona; o desenvolvedor
  percebe imediatamente, em vez de o dado vazar em silêncio.
- O gate transforma "configuramos RLS" em afirmação verificada a cada build.
- O inventário do que é alcançável de fora vira explícito: são as pontes de 0010, e nada
  mais.
- A sentinela diária cobre o caso de uma tabela criada pelo painel, fora do fluxo de
  migrations.

### Negativas
- **Toda tabela nova custa mais.** `revoke all` + grants nominais + `enable rls` + políticas
  antes de qualquer coisa funcionar. São ~40 linhas de SQL a mais por tabela, e é
  intencional.
- **O painel do Supabase fica menos conveniente.** Criar tabela pela UI produz algo que não
  funciona até receber grants por migration. É atrito por desenho, mas é atrito.
- **Pontes são duplicação.** Cada função exposta existe duas vezes — em `app` e a ponte em
  `public`. Uma assinatura alterada precisa ser mudada nos dois lugares.
- `ALTER DEFAULT PRIVILEGES` é por role e por schema; se o Supabase introduzir um role novo
  no futuro, a reversão precisa ser reaplicada. O bloco `DO` já ignora roles inexistentes,
  mas não adivinha roles futuros.

### Neutras
- A postura é mais rígida que a convenção da comunidade Supabase. Quem chegar vindo de
  outro projeto vai estranhar — daí o comentário longo na migration 0009 explicando o
  porquê.

## Como saber que erramos

- O atrito de criar tabela levar a workarounds (gente usando `service_role` para contornar
  grants em vez de escrevê-los).
- As pontes passarem de ~10, indicando que o schema `app` virou API de fato.
- O gate produzir falso positivo recorrente em tabela legítima sem RLS (não deveria existir
  — se existir, o critério é que precisa ser revisto, não a tabela).
