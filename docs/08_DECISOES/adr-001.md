# ADR-001: React + Vite + Supabase direto no front, com toda lógica de dinheiro em Edge Function

**Status:** Aceito
**Data:** 2026-08-17
**Decisores:** Matheus (dono)

## Contexto

O Pautaria nasce em bootstrap pré-receita, com uma pessoa, a partir de um handoff de design
hi-fi. Precisa: autenticação, multi-tenancy com isolamento rígido, realtime para quadros
colaborativos, e cobrança recorrente — tudo em tier gratuito, e no ar rápido.

O projeto também trata dinheiro. Isso muda a conversa: um SaaS de quadros pode viver
inteiro no front; um SaaS de quadros **com assinatura** tem uma superfície que não pode
estar no navegador de jeito nenhum.

## Decisão

**Modelo A (SPA + BaaS)** — React 18 + Vite + TypeScript falando direto com o Supabase via
SDK, com RLS como camada de autorização. **Com uma exceção explícita:** criar, cancelar e
reconciliar assinatura, e processar o webhook da Asaas, rodam em **Supabase Edge Functions**
(Deno) com `service_role`.

Corolários:
- A camada de serviços (`src/lib/*.service.ts`) é a única fronteira com o backend, aplicada
  por ESLint.
- A credencial da Asaas existe apenas em Supabase Secrets — a Vercel nunca a vê.
- Deploy: Vercel (front estático) + Supabase (dados e funções).

## Alternativas consideradas

### A — API própria contract-first (Node + Postgres) desde o início
Mais controle, menos lock-in, contrato explícito. Descartada pelo custo de tempo e infra
numa fase em que a pergunta ainda é "alguém quer isso?". Escrever CRUD, auth e realtime à
mão adiaria o produto em semanas, e o realtime sozinho já é um projeto.

**O que se perde ao descartar:** independência de fornecedor e um contrato de API público.
Mitigado pela camada de serviços — a migração futura mexe em um diretório.

### B — Next.js (App Router) na Vercel
Route Handlers resolveriam a cobrança sem Edge Functions, com um provedor a menos.
Descartada por dois motivos: quebra o padrão da casa (React+Vite) e, mais concreto,
**espalharia o segredo da Asaas por dois provedores** — Vercel e Supabase. Concentrar o
perímetro sensível num lugar só vale mais que a conveniência de deploy.

### C — Supabase puro, cobrança também no front
Descartada de imediato. Colocaria a chave da Asaas no bundle público.

## Consequências

### Positivas
- Do zero ao MVP monetizável em uma fundação, dentro do tier gratuito.
- RLS entrega multi-tenancy sem escrever backend de autorização.
- Realtime de graça.
- O perímetro sensível é pequeno e nomeável: cinco funções em `supabase/functions/`.

### Negativas
- **Lock-in real no Supabase.** RLS, `auth.uid()`, PostgREST e Edge Functions são
  específicos. Sair custa reescrever a camada de dados.
- **Lógica de negócio dividida** entre policies SQL, triggers e TypeScript. Quem chega
  precisa ler as migrations para entender o produto — não basta ler o front.
- **Depurar RLS é chato.** O erro típico é uma consulta que volta vazia, sem dizer por quê.
  Mitigado pelo teste de isolamento, que exercita as políticas de verdade.
- Duas plataformas para operar em vez de uma.
- Latência extra no checkout: browser → Edge Function → Asaas.

### Neutras
- Deno nas funções e Node no front: dois runtimes, duas formas de importar dependência.
  Custou uma duplicação consciente (`documento.ts` existe nos dois lados, documentada).

## Como saber que erramos

- Volume de consultas em que a RLS vira gargalo mensurável.
- Necessidade de um segundo consumidor da API (app mobile nativo, integração de parceiro).
- Lógica de negócio migrando para as Edge Functions a ponto de elas virarem, de fato, uma
  API própria mal organizada — nesse caso, assuma e escreva a API.
- Limite do tier gratuito do Supabase virando restrição de produto, não de custo.
