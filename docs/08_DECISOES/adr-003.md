# ADR-003: O ofício é dado, não código

**Status:** Aceito
**Data:** 2026-08-17
**Decisores:** Matheus (dono)

## Contexto

O protótipo de design trazia a configuração dos nichos como um objeto JavaScript:

```js
NICHES = {
  mkt: { nome:'Marketing', glifo:'▲', hue:45, etapas:[...], f1:'Canal', ... },
  ti:  { ... }, prod: { ... }
}
```

Funciona perfeitamente para um protótipo. A pergunta era o que fazer com isso na
implementação — e a resposta define se o produto escala em nichos ou não.

O modelo de negócio depende disso: a hipótese central é que dá para vender o mesmo produto
para social media, dev e autônomo **porque cada um recebe um sotaque diferente**. Se cada
sotaque novo custar um ciclo de desenvolvimento, a hipótese não fecha.

## Decisão

Toda a configuração do ofício vive no banco: `oficios`, `oficio_etapas`,
`oficio_templates`, `oficio_exemplos`.

**Um ofício novo é um `INSERT`. Zero linhas de React, zero deploy.**

Corolários que a decisão impõe ao código:
- Nenhum componente conhece o nome de um ofício. Zero ocorrências de `'mkt'`, `'Canal'` ou
  `hue === 45` em `src/components/`.
- A identidade visual é guardada como `(hue, chroma)` e o accent é **derivado** em OKLCH —
  não como quatro strings hexadecimais.
- Os modos `mono` e `solo` são colunas booleanas, não condições no componente.
- Ofício com `workspace_id IS NULL` é do sistema; com valor, é do tenant (planos pagos).

## Alternativas consideradas

### A — Manter o objeto de configuração no código
Mais simples, com tipagem completa e sem consulta ao banco no carregamento. Descartada
porque um ofício novo viraria PR + review + deploy, e um ofício **de cliente** seria
impossível sem branch por cliente — exatamente o que `memory/restrictions.md` P2 proíbe.

### B — JSON versionado no repositório, carregado em runtime
Meio-termo: sem deploy de código, mas ainda sem ofício por tenant, e sem forma de a UI
editar. Adiaria o problema sem resolvê-lo.

### C — Ofício totalmente livre, com N campos customizados
O oposto: o usuário define quantos campos quiser. Descartada por contrariar a visão —
`docs/00_VISAO` diz explicitamente que o Pautaria **não** é um construtor de banco de dados
sem código. Dois campos com rótulo do ofício é uma restrição de produto, não uma limitação.

## Consequências

### Positivas
- Um nicho novo (jurídico, obra, consultório) custa um `INSERT` e algumas horas de pesquisa
  sobre o vocabulário daquele ofício — não um ciclo de desenvolvimento.
- Ofício personalizado por tenant vira feature natural, não reescrita.
- A UI fica genuinamente genérica, e isso é verificável: basta procurar por nome de ofício
  em `src/components/`.
- Guardar `(hue, chroma)` em vez de hexadecimais torna impossível cadastrar uma paleta
  "quase certa" — as quatro variações saem corretas por construção.

### Negativas
- **Mais uma consulta antes da primeira tela.** Mitigado trazendo etapas e templates
  aninhados numa consulta só — mas é latência que o objeto em código não teria.
- **Tipagem mais fraca.** `oficio.campo1Label` é `string`; o compilador não sabe que para
  o ofício `mkt` ele vale `'Canal'`. Perde-se autocompletar e checagem exaustiva.
- **Dado de configuração precisa de migration e seed**, com toda a cerimônia disso —
  incluindo idempotência para `db reset` funcionar.
- **Erro de cadastro vira bug de produção sem passar por review de código.** Um ofício com
  zero etapas quebraria o quadro. Mitigado por CHECKs, mas o risco existe.
- Etapas em tabela separada tornam a reordenação um problema real (resolvido com constraint
  deferrable).

### Neutras
- Os três ofícios do sistema são semeados por SQL. Editá-los é migration, não clique — o
  que é desejável: eles são a experiência de entrada do produto.

## Como saber que erramos

- Se, depois de seis meses, ainda existirem exatamente três ofícios: a flexibilidade não se
  pagou, e o objeto em código teria bastado.
- Se a consulta de ofício aparecer como gargalo no carregamento inicial.
- Se a falta de tipagem forte gerar uma classe recorrente de bug.
- Se usuários pedirem consistentemente mais de dois campos livres — aí a decisão de produto
  em `docs/00_VISAO` é que precisa ser revisitada, antes desta.
